# Gaming-Room
The Gaming Room made a game for Andriod based on a game show, and they called it Draw It or Lose it. In this game, contestants would have a picture draw on their screens and they would have 45 seconds to answer it, then the other team would get a chance to steal the points for the last 15 seconds. Their goal for me was to decide a platform that would allow them to expand their product to other operating platforms. I wrote a summary of what was needed for them to expand, what each operating platform had to offer, and afterwards, explaining which one was best and why. I feel like the best part of my documentation was the understanding of what they needed in order for them to expand. Using the UML diagram, I understood what they wanted coded and was able to write a summary of the domain model and I was able to document the requirements. The thing I needed the most work on, however, was the design constraints. I could have gone more into detail on what each constraint needed and really highlighted the constraints of their goals. The way I could best fix this issue is by talking in details about each constraint rather than just listing them all in a paragraph. Things like requiring a network connection, could be explained better by listing how it is a constraint. The thing I found most helpful about working on a design document while developing code is the fact that you get a bigger picture and write it down. I think that understanding, for me, diagrams like a UML help the most. This is because I can have a bigger visual of how the code is meant to exist by using real ideas and give me more actionable steps for it. I interpreted the user's needs by writing them into actionable steps on my design document. The reason this step is important is it's their product it should meet their goals, and in a design document you can fact check with them that you meet all their goals before you send it to code. This means we don't have to go back over details missed in post and edit their product after the fact. For me, the first step to designing software is understanding the user and owners needs then making a diagram then coding it. These steps in this order help ensure product quality by fact checking along the way that the product meets demands through documentation. It also helps create a mental note of all the things needed to be added to system before sending it out, and it helps create timelines and set up goals for different teams if more than one person is required to complete the project.
